# Работа над проектами 3piroga и DUXI в общем репозитории MyAdmin

Сначала определи проект задачи по запросу пользователя и фактическому `APP_PROJECT`, затем применяй соответствующий раздел ниже. `myadmin` — общая Laravel/Filament-админка для нескольких проектов, поэтому не переноси проектные правила одного сайта на другой.

# Проект 3piroga

Эти правила действуют, когда задача относится к проекту 3piroga. `myadmin` — общая Laravel/Filament-админка с другими проектами и пакетами; не считай весь репозиторий кодом 3piroga. Если принадлежность задачи в общем коде неясна, уточни проект до изменения поведения других проектов.

## Границы изменений

- Фронтенд 3piroga меняй только в `packages/frontend-3piroga/`. Это отдельный Git-репозиторий; проверяй его статус и diff отдельно от корневого репозитория. Не меняй `packages/frontend-sevia/` и другие фронтенды ради задачи 3piroga.
- Общие `app/`, `routes/`, `config/`, `resources/` и админка Filament доступны для изменений, когда задача этого требует. Перед изменением общего кода проверь, как оно повлияет на другие проекты, и по возможности ограничь проектное поведение через `config('project.name')` или существующую конфигурацию.
- Сохраняй посторонние локальные изменения и сгенерированные файлы; не смешивай правки двух Git-репозиториев при проверке и отчёте. Не делай commit/push без просьбы пользователя.

## Конфигурация и данные

- Проект выбирается `APP_PROJECT=3piroga`. Сопоставление в `config/projects.local.php`: тема `3piroga`, фронтенд `frontend-3piroga`, база MySQL `myadmin`. Не полагайся на значение по умолчанию в `config/project.php` как на доказательство активного проекта.
- Перед любой командой, меняющей БД (миграция, сидер, tinker, SQL), проверь фактические `APP_PROJECT`, `DB_CONNECTION`, итоговое имя БД и влияние кэша конфигурации. Если окружение не указывает однозначно на 3piroga/`myadmin`, остановись и согласуй переключение; не переписывай `.env` молча. Не показывай секреты из `.env` в ответе.
- Миграции схемы создавай только в общей админке `database/migrations/` при изменении или создании её модулей/таблиц. Не добавляй миграции в пакет фронтенда. Поскольку миграции общей админки могут выполняться и для других БД, делай их совместимыми либо явно ограниченными проектом; при неоднозначном влиянии уточни решение.
- Переводы и проектные текстовые данные не оформляй миграцией: для воспроизводимого изменения используй сидер в `database/seeders/`. До создания/применения перевода спроси пользователя, нужен сидер или прямая запись в БД. Прямую запись делай только после выбора пользователя и проверки целевой БД; не заменяй существующие переводы без оценки последствий. Для сидеров предпочитай повторно запускаемые операции и существующий формат `uk`/`ru`/`en`, когда он применим.
- Создание файла миграции/сидера не означает разрешения на его выполнение. О запуске на конкретной БД договаривайся отдельно, если это не было явно частью задачи.

## Проверка и результат

- Проверяй только затронутые части. `npm run build` собирает также `frontend-sevia` и меняет общие `public/build`; перед сборкой оцени её побочные эффекты и не включай чужие артефакты в результат.
- В ответе укажи, что изменено в админке и что — в отдельном фронтенд-репозитории, какие проверки прошли и запускались ли миграции/сидеры/записи в БД.

# Проект DUXI

Эти правила действуют, когда задача относится к проекту DUXI. `myadmin` — общая Laravel/Filament-админка для нескольких проектов: код админки общий, а данные проектов разделены по разным базам. Не считай весь репозиторий кодом DUXI. Если из задачи неясно, относится ли изменение общего поведения только к DUXI или ко всем проектам, уточни это до изменения общей логики.

## Границы изменений

- Фронтенд DUXI находится только в `packages/frontend-sevia/`. Это отдельный Git-репозиторий; проверяй его статус и diff отдельно от корневого репозитория. Не меняй `packages/frontend-3piroga/` и другие фронтенды ради задачи DUXI.
- Общие `app/`, `routes/`, `config/`, `resources/`, `database/` и админка Filament доступны для изменений, когда задача этого требует. Учитывай, что эти изменения могут повлиять на все проекты, подключённые к общей админке.
- Не дублируй общую административную логику во frontend-пакете. Проектное поведение ограничивай через существующую конфигурацию и `config('project.name')` только тогда, когда оно действительно должно отличаться для DUXI.
- Сохраняй посторонние локальные изменения и сгенерированные файлы. Не смешивай правки корневого репозитория и отдельного frontend-репозитория при проверке и отчёте. Не делай commit или push без прямой просьбы пользователя.

## Конфигурация и базы данных

- Проект выбирается через `APP_PROJECT=duxi`. Сопоставление в `config/projects.local.php`: тема `duxi`, frontend-пакет `frontend-sevia`, база MySQL `duxi`. Не полагайся на значение по умолчанию в `config/project.php` как на доказательство активного проекта.
- Админка и схема приложения общие, но каждый проект подключается к своей базе. Перед любой командой, которая читает или меняет проектные данные либо схему (`migrate`, сидер, `tinker`, SQL и подобные команды), проверь фактические `APP_PROJECT`, `DB_CONNECTION`, влияние `DB_URL`, итоговое имя базы и кэш конфигурации.
- Если окружение не указывает однозначно на `APP_PROJECT=duxi` и базу `duxi`, не выполняй команду, меняющую БД, и согласуй переключение с пользователем. Не переписывай `.env` молча и не показывай его секреты в ответе.
- Миграции общей схемы создавай только в `database/migrations/`, не во frontend-пакете. Делай их безопасными для последовательного применения к отдельным базам всех проектов. Не ограничивай миграцию только DUXI без явного требования и оценки влияния на общую админку.
- Проектные данные и переводы не оформляй миграциями. Для воспроизводимых изменений используй повторно запускаемые сидеры в `database/seeders/` либо прямую запись в целевую БД — только после согласования способа с пользователем и проверки, что выбрана база `duxi`.
- Не запускай `ProductCategoryIconsSeeder` для DUXI: этот существующий сидер предназначен только для `APP_PROJECT=3piroga`.
- Создание миграции или сидера не означает разрешения на их запуск. Выполняй их на конкретной базе только если это прямо входит в задачу или отдельно согласовано.

## Проверка и результат

- Проверяй только затронутые части. Для точечной production-сборки DUXI используй режим `vite build --mode frontend-sevia`, если сборка нужна. Не запускай без необходимости общий `npm run build`: он собирает админку, `frontend-3piroga` и `frontend-sevia`, меняя общие и чужие артефакты в `public/build`.
- Для изменений frontend DUXI запускай подходящие проверки внутри `packages/frontend-sevia/`, если они предусмотрены его инструментами. Для общей админки запускай только релевантные Laravel/PHP-проверки.
- В итоговом ответе отдельно укажи, что изменено в общей админке и что — в `packages/frontend-sevia/`, какие проверки прошли и запускались ли миграции, сидеры или прямые записи в БД.
